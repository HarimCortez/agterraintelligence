> Scoped requirements addendum to the controlled `REQUIREMENTS.md`. This document does not supersede or re-derive `REQUIREMENTS.md` — it is the `pm`-produced detail spec for two specific screens (`Report Selection & Purchase`, `Purchased Report Workspace`) that a 2026-09-17 UX audit confirmed are entirely missing from the investor app, even though the backend (`apps/api/src/monetization/`) already implements most of the capability they need. Where `REQUIREMENTS.md` has already resolved a business question (pricing, tiers, upgrade-credit), this document cites the exact resolved rule rather than re-deciding it. Treat this as controlled input for `ux`/`fe`/`be`/`data` on the same terms as `REQUIREMENTS.md` itself — escalate conflicts through the Development Director rather than reinterpreting.

## Objective

Ship the missing "Purchase Intelligence" and "Decide" steps of the approved investor workflow (`REQUIREMENTS.md` Workflow section: *Discover → Rank → Investigate → Compare → **Purchase Intelligence** → **Decide** → Monitor → Manage*). Today there is no "unlock report" CTA, no tier-selection screen, and no purchased-report view anywhere in `apps/investor-web` — despite `apps/api/src/monetization/` already implementing report-tier pricing, checkout-session creation, upgrade-credit computation, and order/content retrieval end to end. This is a UI/product-completeness gap on top of an existing backend capability, not a net-new subsystem.

## User

The investor who has already discovered, ranked, and investigated a specific property (has visited its Property Intelligence Page, possibly compared it against others) and is now deciding whether to pay for deeper, persisted AI due diligence before committing further time or capital. Applies to every external role — report purchase is explicitly **not** gated by subscription tier (see Business Rules).

## User Story

- As an investor viewing a property, I want to see an "Unlock Report" call to action that takes me to a tier-selection screen, so that I can choose how deep an analysis I want to pay for.
- As an investor on the Report Selection & Purchase screen, I want to see what each purchasable tier includes, its price (and, if I've already purchased a lower tier on this same property, my upgrade credit applied), so that I can make an informed purchase decision and never pay twice for the same intelligence.
- As an investor who has just completed a report purchase, I want to land on a workspace showing my report's status and, once ready, its full content, so that I can act on the "Decide" step of my workflow without having to hunt for it.
- As an investor who owns one or more purchased reports, I want a way to find any of them again later (from the property page at minimum), so that a report I paid for is never effectively lost.

## Workflow

1. Investor is on the **Property Intelligence Page** (`/properties/[id]`) → clicks **Unlock Report** (already a named action in `REQUIREMENTS.md` Section 5.3's action list, `unlock report` — currently not implemented in `apps/investor-web`).
2. Investor lands on **Report Selection & Purchase** for that property → sees tier cards (Essential, Investor, Professional, Premium-visible-but-not-purchasable), each priced per the investor's own subscriber/non-subscriber status, with upgrade credit pre-applied if applicable → selects a tier → purchase.
3. Purchase hands off to the existing Stripe Checkout flow (out of scope for this document — see Explicit Scope Boundary).
4. On successful payment, investor is returned to the app and lands on (or is clearly, immediately routed to) the **Purchased Report Workspace** for that specific order — not a generic account page (see Business Rules / Dependencies: the current redirect target is a gap, not yet resolved).
5. While the order is `queued`/`generating`, the workspace shows a real in-progress state (not a blank/broken page). Once `delivered`, the full report content renders.
6. Investor can return to any previously purchased report later — at minimum via the Property Intelligence Page for that property (see Functional Requirements — "My Reports" is flagged as an open scope question, not assumed).

## Functional Requirements

### Report Selection & Purchase (`/properties/[id]/reports` or equivalent route — routing decision is `ux`/`fe`'s, not asserted here)

1. **Entry point.** A visible "Unlock Report" (or equivalent labeled) CTA must exist on the Property Intelligence Page for every property, per `REQUIREMENTS.md` Section 5.3's action list. It must be reachable by every authenticated investor regardless of subscription tier (Business Rule 1).
2. **Tier presentation.** The screen must show all four report tiers (Essential, Investor, Professional, Premium Intelligence) as tier cards, sourced from `GET /v1/report-tiers` (already implemented, public). Each card must show: display name, price, and (Premium only) that it is not currently purchasable.
   - Premium Intelligence must remain visible for pricing-page completeness (per `REQUIREMENTS.md` decision log #10) but its CTA must be disabled/non-purchasable, with a clear reason shown (e.g., "Requires analyst review — not yet available for purchase"), matching the API's explicit 400 (`"Premium reports are not yet available for purchase"`) rather than a generic error if the user somehow reaches checkout for it.
3. **Subscriber vs. non-subscriber pricing.** The price shown for each purchasable tier must reflect the investor's actual subscription status at view time — subscriber price if the investor has an `active` subscription, non-subscriber price otherwise (Business Rule 2). The screen must make this distinction visible, not just silently show one number — a non-subscriber must be able to see that a paid plan would lower this and future report prices (per `REQUIREMENTS.md` Decision 4's requirement that the "upgrade to save" comparison be surfaced).
4. **Upgrade credit.** If the investor has a `delivered` report order for this same property at a lower tier than the one they're viewing/selecting, the screen must show the applicable upgrade credit and the resulting net price *before* the investor commits to purchase — not only after. The credit shown must match what `POST /v1/properties/:id/reports/checkout` will actually charge (computed server-side against the price the investor actually paid for the prior tier, per Business Rule 3) — the UI must not independently recompute or estimate this value, only display what the backend returns/will return.
5. **Already-owns-this-tier-or-higher.** If the investor already has a `delivered` order at the selected tier or higher for this property, the purchase action for that tier (and any lower tier) must be disabled/replaced with a "view your report" affordance rather than allowed to proceed to checkout and fail with a 409 (Business Rule 4, Edge Cases).
6. **Report comparison content.** Per `REQUIREMENTS.md` Section 5.4 ("report tier cards/pricing, recommended report, comparison matrix, upgrade logic, purchase confidence"), the screen must let the investor compare what each tier includes at a glance. **What each tier's content actually differs by is: depth of the same AI-generated investment analysis (Essential = thesis-depth; Investor/Professional = progressively more evidence, scenario, and risk framing), not access to different data sources** (per `REQUIREMENTS.md` decision log #10 — comparables/ownership/regulatory tiering was descoped because the underlying data doesn't exist yet). Tier-comparison copy must describe this accurately (depth/thoroughness, not fabricated content categories) — this is a hard constraint on copy accuracy, not a presentation preference.
7. **Purchase action.** Selecting a tier and confirming purchase calls `POST /v1/properties/:id/reports/checkout` (already implemented) and redirects the investor to the returned Stripe-hosted `checkoutUrl`. This document does not specify anything about the Stripe/payment integration itself (see Explicit Scope Boundary).
8. **Logged-out access.** An unauthenticated visitor must be able to see report tiers and pricing (public data) but must be prompted to log in/register before a purchase can proceed — attempting to purchase while logged out must never reach a raw 401 from the API; it must be intercepted client-side with a login prompt that returns the user to this same screen/tier selection afterward.

### Purchased Report Workspace (`/report-orders/[id]` or equivalent — routing decision is `ux`/`fe`'s)

9. **Access point after purchase.** After a successful purchase, the investor must be taken to (or given an unambiguous, immediate way to reach) the Purchased Report Workspace for that specific order — not left on a generic confirmation screen with no path to their report. (Flagged in Dependencies: the currently-implemented Stripe redirect target does not yet support this — see below.)
10. **Order status states.** The workspace must render a distinct, real UI state for each `ReportOrder.status` value it can actually reach in this pass (`pending_payment`, `queued`, `generating`, `delivered`, `failed`) — per the Edge Cases in `REQUIREMENTS.md` ("Locked content viewed without entitlement... must render a teaser/explainer, never raw restricted content and never a hard blank" — the same spirit applies to an in-progress or failed report, which must never render as a blank or broken page). `awaiting_review`/`approved`/`refunded` exist in the schema for Premium's future human-review path and refund handling respectively and are out of scope for this pass's purchasable tiers, but the workspace must not crash or blank-screen if it ever encounters them.
11. **Delivered report content.** Once `status: "delivered"`, the workspace must render the report's persisted `content` — the same six-field AI Response Pattern structure already mandated platform-wide (`REQUIREMENTS.md` Section 8.3: Conclusion → Evidence → Risks → Confidence → Sources → Next action) and already used by the free AI Analyst and this report-generation path (`apps/api/src/monetization/report-generation.service.ts` reuses the identical `submit_analysis` tool/schema, only the prompt depth differs by tier). Do not invent a different report layout/section set than this six-field structure for v1 — the backend does not produce anything richer than this today.
12. **Report identification.** The workspace must clearly show which property and which tier the report is for (property address/name, tier display name, purchase date, price paid) — an investor with more than one report must never be confused about which one they're viewing.
13. **Re-access.** A `delivered` report must remain viewable by the purchasing investor indefinitely (no expiry) by returning to the workspace — at minimum, the Property Intelligence Page for that property must surface a link/affordance to any of the investor's existing report orders for that property (backed by the already-implemented `GET /v1/properties/:id/reports`), so a purchased report is never accessible only via a one-time post-purchase redirect.
14. **"My Reports" across properties — confirmed OUT of scope for this pass (Product Owner decision, 2026-09-18).** Per-property access (Functional Requirement 13) is sufficient. No cross-property reports index screen and no new "list all my orders" endpoint are to be built in this pass.
15. **Failed report.** If `status: "failed"`, the workspace must clearly tell the investor the report failed to generate and that this has been flagged for follow-up — per `REQUIREMENTS.md`'s decision log #10 gap note, no automatic refund is issued; the investor-facing copy must not promise one. It should point the investor at the existing Support Center (`apps/investor-web/src/app/support/`) to file a ticket if not already automatically actionable.
16. **Report Q&A / upgrade / watch / compare actions.** `REQUIREMENTS.md` Section 5.5 lists "download PDF, ask AI, upgrade report, watch, compare" as actions on this screen. **PDF download is explicitly out of scope for this pass** (`REQUIREMENTS.md` decision log #10: "a report is a page in the app, not a downloadable file, for this pass") — do not build a PDF export affordance. "Ask AI," "upgrade report," "watch," and "compare" affordances on this screen are in scope to the extent the underlying capability already exists elsewhere in the app (AI Analyst drawer, watchlist, comparison tray) — this document does not re-specify those subsystems, only that this screen should surface entry points into them consistent with how the Property Intelligence Page already does.

## Business Rules

Extracted verbatim/near-verbatim from `REQUIREMENTS.md`'s Key Product Decisions and confirmed in the actual implementation (`apps/api/src/monetization/report-orders.service.ts`) — do not re-derive or alter these:

1. **No subscription-tier gating on report purchase eligibility.** Per Decision 4: "Report purchases are not gated by subscription tier — any authenticated user (including Free tier) can buy any report tier [that is currently purchasable]." This resolves `REQUIREMENTS.md` Open Question 14. Premium is the sole exception, and that exception is about human-review-pipeline readiness, not subscription tier.
2. **Subscriber vs. non-subscriber pricing (Decision 9), confirmed launch prices:**
   - Subscriber price: Essential $49, Investor $99, Professional $249, Premium Intelligence $499 (not purchasable).
   - Non-subscriber price (+50%, per Decision 9): Essential $73.50, Investor $148.50, Professional $373.50, Premium $748.50.
   - "Subscriber" = the investor has a `Subscription` row with `status: active` at the time of purchase (matches the implemented check).
3. **Upgrade credit rule (Decision 9's closing clause + implementation):** computed against the price the investor *actually paid* for their best already-`delivered` lower tier on that same property — never against list price — capped so the credit never exceeds the new tier's base price (net price floored at $0).
4. **Cannot re-purchase an owned tier or lower.** If the investor already holds a `delivered` order at the requested tier or higher for that property, the purchase is rejected (409, "You already have this report tier or higher for this property"). The UI must prevent this attempt proactively (Functional Requirement 5), not merely handle the resulting error.
5. **Premium is not purchasable in this pass.** Visible for pricing-page completeness; any purchase attempt is rejected with a specific message, not a generic error (Decision 3 + Decision 10).
6. **A purchased/delivered report does not expire and is not shared.** No time-limited or seat-limited access rule anywhere in `REQUIREMENTS.md` for reports; ownership is per-`userId` (`ReportOrder.userId`), scoped via `AccountContext`, with no sharing mechanism implemented or specified. Treat access as permanent, single-account, for this pass.
7. **No PDF deliverable in this pass.** Per Decision 10, a report is an in-app page, not a downloadable file.
8. **Locked-intelligence pattern applies to unpurchased tiers.** Per `REQUIREMENTS.md` Section 8.2: paid/locked content must remain visible in description (what it is, what tier unlocks it, price) but never expose actual restricted content.

## Edge Cases

1. **Purchase failure (payment declined/abandoned at Stripe).** Out of scope to specify Stripe-side handling, but the product requirement is: the investor must be returned to a recognizable state in the app (not stranded on Stripe, not shown as if they own the report) and must be able to retry. A `ReportOrder` remains `pending_payment` indefinitely if payment never completes — the UI must not treat it as in-progress toward delivery when the investor returns later without having paid.
2. **Already owns this tier or higher.** Covered under Functional Requirement 5 / Business Rule 4 — must be prevented proactively in the UI, and if attempted anyway, the API's 409 must be surfaced as a clear message, not a generic error.
3. **"Downgrade" attempt (selecting a lower tier than one already owned).** Same rejection path as #2 — the API treats "requested tier ≤ any already-owned tier's sort order" as the same 409. The UI must not present already-owned-or-lower tiers as purchasable at all.
4. **Logged-out user attempting to purchase.** Must be intercepted client-side with a login/register prompt (Functional Requirement 8) — must never surface a raw 401.
5. **Property becomes unavailable/delisted/sold after report purchase.** **Confirmed (Product Owner decision, 2026-09-18): the report remains fully viewable regardless of the property's current listing status.** No restriction, banner-gating, or access change is tied to listing status changes.
6. **Report generation fails after successful payment.** Already covered by an explicit, confirmed decision (Decision 10's gap note): order goes to `failed`, no automatic refund, investor must be told plainly and pointed at Support (Functional Requirement 15). This is decided, not open.
7. **Investor revisits Report Selection & Purchase after abandoning an earlier checkout (`pending_payment` order exists, no `delivered` order).** The screen must not block a fresh purchase attempt — a `pending_payment` order does not count as "already owns this tier" in the existing service logic. The UI should not display a stale `pending_payment` order as if it were an active/owned report.
8. **Subscription status changes between viewing the pricing screen and completing checkout.** The price actually charged is whatever the backend computes at checkout-creation time, not what was displayed earlier in the session.

## Acceptance Criteria

1. Every property's Property Intelligence Page shows an "Unlock Report" CTA, for subscriber, non-subscriber, and logged-out visitors (leading to a login prompt per Edge Case 4).
2. On Report Selection & Purchase for a given property, all four report tiers are displayed with the investor's actual applicable price, sourced from live API data, matching `GET /v1/report-tiers` values exactly (no hardcoded prices in the frontend).
3. For an investor with a `delivered` Essential-tier report on Property X, viewing the Investor or Professional tier for Property X shows the correct upgrade credit and net price, matching what `POST /v1/properties/:id/reports/checkout` actually returns/charges for that same request.
4. For an investor with a `delivered` Investor-tier (or higher) report on Property X, the Essential and Investor tier purchase actions for Property X are disabled/replaced with a "view your report" affordance.
5. Selecting Premium shows it as not-yet-purchasable with an explanatory message; no checkout attempt is initiated for Premium from the UI.
6. Completing a successful test-mode Stripe Checkout for a report returns the investor to a Purchased Report Workspace scoped to that specific order — or, if the redirect-target gap (Dependencies) is not yet resolved, the investor can reach that same workspace within one additional click from wherever they land, with the correct order pre-identified.
7. While an order's status is `queued` or `generating`, the Purchased Report Workspace shows an explicit in-progress state (not blank, not an error, not the appearance of a delivered report).
8. Once an order's status is `delivered`, the workspace renders the report's Conclusion / Evidence / Risks / Confidence / Sources / Next-action content in full, correctly attributed to the right property and tier.
9. If an order's status is `failed`, the workspace tells the investor plainly that generation failed and does not claim a refund has been or will be automatically issued.
10. A `delivered` report remains reachable by the purchasing investor on a later visit via at least the Property Intelligence Page for that property.
11. No report tier's marketing/comparison copy claims access to comparables, ownership records, or regulatory data beyond what decision log #10 confirms is actually generated (AI-analysis depth only) — a manual copy review against that decision log passes.
12. No PDF download affordance exists anywhere on the Purchased Report Workspace for this pass.

## Dependencies

1. **Backend capability already exists and should be reused, not rebuilt:** `GET /v1/report-tiers`, `POST /v1/properties/:id/reports/checkout`, `GET /v1/properties/:id/reports`, `GET /v1/report-orders/:id` — all implemented in `apps/api/src/monetization/`. Stripe integration itself is out of scope per the Product Owner's sequencing (see Explicit Scope Boundary).
2. **Post-purchase redirect currently does not point at a specific report.** `apps/api/src/monetization/checkout-urls.ts` sends both subscription and report checkout success/cancel redirects to the generic `${FRONTEND_URL}/account?checkout=success|cancelled` — no `reportOrderId`/property context is carried through today. Functional Requirement 9 / Acceptance Criterion 6 need this closed — small, scoped `be` change, flagged for `arch`/`be` to scope, not designed here.
3. ~~No "list all my report orders" endpoint exists.~~ **Resolved: not needed — "My Reports" is confirmed out of scope for this pass (Functional Requirement 14).**
4. Depends on `ux` for actual screen layout, states, and interaction design for both screens — this document defines requirements, not screens.
5. Depends on the existing AI Analyst drawer, Watchlist, and Comparison Workspace subsystems for the "ask AI / watch / compare" entry points (Functional Requirement 16).
6. Depends on the existing Support Center (`apps/investor-web/src/app/support/`) for the failed-report follow-up path (Functional Requirement 15).

## Explicit Scope Boundary

This document does not design, review, or specify anything about the Stripe/payment integration itself — that work already exists in `apps/api/src/monetization/stripe-client.service.ts` / `stripe-webhook.service.ts` and is deliberately deferred for a separate billing-focused review pass, per the Product Owner's own sequencing (UX/customer journey first, billing review last). Requirements here assume "a purchase mechanism exists and will be wired up/reviewed later" and focus only on user-facing tier selection, pricing display, purchase-outcome states, and purchased-report access.
